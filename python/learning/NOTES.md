# Teaching Notes

## Preferences

- Use short, step-by-step explanations and one active coding task.
- Prefer editable `.py` files and real interpreter output over long HTML lessons.
- Explain syntax and behaviour before expecting independent recall.
- Compare with JavaScript and PowerShell when useful.
- Use repeated retrieval and changed examples to build fluency.
- Provide a focused official documentation link for each new topic.
- Review Sat's code before giving a complete answer.
- Use a long project path with repeated coding, practical quizzes and cumulative
  phase gates rather than a short twelve-project overview.
- Present quiz questions one at a time and repair gaps through changed code.
- Use UK English and do not use em dashes.
- Keep teaching rapid and flowing. Ignore spelling mistakes in chat unless they
  prevent understanding or affect the Python concept, code, command or output
  being assessed.
- Before every learner action, briefly explain why the action matters and how it
  supports the current project or practical infrastructure work.
- When introducing syntax, name what each construct is, such as a function,
  method, variable, argument or returned value, before asking Sat to type it.
- For rapid practice, Sat can save the file and say `done`; the tutor should run
  the current file with safe fictional inputs and inspect the real output.
  Require Sat to use the terminal only when command execution is being assessed.

## Prior knowledge

- Sat has basic Python and JavaScript exposure.
- PowerShell practice has included variables, input, arrays, loops, objects,
  filtering, sorting and functions with guidance.
- Independent Python project evidence has not yet been recorded in this course.

## Constraints

- Some sessions happen while travelling, so exercises should remain small and
  usable offline after sources are saved.
- Do not treat copied code or a successful guided run as mastery.
- Use fictional support and infrastructure data.
- Do not access live organisational systems or secrets.
- The Python tutor owns language and software-engineering progress. The Linux
  tutor owns operating-system administration, even when a Python project runs on Linux.
